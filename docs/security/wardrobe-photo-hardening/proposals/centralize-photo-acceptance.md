# Security Hardening Proposal: 옷장 사진 승인 경계 통합

## Decision

신규 사진 아이템을 저장할 수 있는 권한을 UI 상태가 아니라 서버의 검증된 승인 결정에 연결할지 결정해야 함. 함께 결정할 범위는 의미 판별, 파일 검증, 남용 제한, 로그, 로컬 보관, 사용자 고지임.

## Executive Recommendation

검토할 안은 옵션 1 `UI·프롬프트 보강`, 옵션 2 `중앙 실패-폐쇄 승인 게이트`, 옵션 3 `온디바이스+중앙 이중 게이트`임. 현재 앱 규모와 네이티브 복잡도를 고려해 옵션 2를 권고함. 옵션 3은 사람 또는 민감 사진이 네트워크로 나가는 것 자체를 줄이는 것이 최우선 요구일 때 우선순위가 올라감.

## Evidence

관련 호출자와 정책 화면을 직접 확인했음. 가장 큰 구조적 근거는 분석 실패 뒤에도 신규 사진을 저장할 수 있는 `E2`와, 서버가 허용 여부가 아닌 의류 속성만 반환하도록 강제하는 `E3`임.

| Evidence | Finding or document | What it establishes |
| --- | --- | --- |
| `E1` | 모바일 사진 선택·정규화·전송 | OS 이미지 선택, JPEG 재인코딩, EXIF 미요청, 약 1.45M base64 제한, 인증 요청이 존재함. 클라이언트 검증은 신뢰 경계가 아님. |
| `E2` | 사진 등록 UI와 수동 저장 우회 | 분석 실패 시 직접 입력 저장이 가능하며 신규 사진에 서버 승인 증명이 필요하지 않음. |
| `E3` | 서버 사진 분석 경계 | 로그인과 크기 제한은 있으나 base64 문자·길이만 검사하고, 프롬프트는 비의류 거절 결정을 요구하지 않음. |
| `E4` | App Attest 검증과 모니터 모드 | 실패가 기록되지만 `monitor` 모드에서는 요청이 계속됨. |
| `E5` | Cloudflare Worker 라우팅 | 사진 분석은 Worker에서 직접 AI binding으로 전달됨. 별도 이미지 저장 binding은 현재 경로에 없음. |
| `E6` | 카메라·사진 보관함 권한 선언 | 목적 문자열과 Android 카메라 권한은 있으나 업로드 직전의 세부 처리 고지는 아님. |
| `E7` | 앱 내 개인정보처리방침 요약 | 옷장 이미지와 AI 처리·저장 여부가 앱 내 요약에 반영되지 않음. |
| `E8` | 배포용 개인정보처리방침 | 옷장 이미지는 선택 정보로 적혀 있으나 Workers AI 추론 전송·비저장·처리 지역 설명이 명확하지 않음. |

관찰 사실에서 한 단계 추론하면, 현재 승인 정책의 소유자가 없음. UI는 실패를 우회할 수 있고 서버는 어떤 사진이 와도 의류 카테고리 중 하나를 만들도록 요구함. 따라서 정상 사용자 실수와 변조 클라이언트 모두 비의류·민감 사진을 처리 경계로 보낼 수 있음.

## Current Design And Failure Mode

[현재 구조](../diagrams/centralize-photo-acceptance-before.mmd)는 사진을 기기에서 JPEG로 다시 만들고 인증된 JSON 요청으로 전송함. 이 과정은 원본 EXIF를 직접 보내지 않고 크기를 낮추는 장점이 있음. 서버도 세션과 App Attest를 확인하고 base64 길이를 제한함. Cloudflare 공식 문서상 Workers AI 입력은 고객 콘텐츠이며 명시적 저장 서비스를 함께 쓰지 않는 한 저장되는 구조는 아님.

문제는 정책 결정이 끝까지 이어지지 않는 점임. 모델이 실패하면 UI가 수동 분류 저장을 허용하고, 모델이 성공해도 비의류 여부를 반환할 필드가 없음. 서버는 실제 JPEG/PNG/WebP 시그니처나 디코딩 크기를 검증하지 않고, Worker 본문은 `request.text()`로 모두 읽은 뒤 애플리케이션 크기를 검사함. 사용자별 호출 제한과 정확한 일일 비용 예산도 없음. App Attest는 현재 모니터 모드라 자동화된 정식 클라이언트 외 호출을 차단하지 못함.

## Desired Invariants

- 신규 사진 아이템은 서버가 현재 정책 버전으로 `accept`한 경우에만 저장 가능해야 함.
- `reject`, `review`, 모델 오류, 시간 초과, 낮은 신뢰도는 모두 저장 불가로 처리해야 함.
- 승인 대상은 한 장의 의류·신발·가방·착용 액세서리 하나로 한정해야 함.
- 사람·얼굴·신체 중심 사진, 민감 콘텐츠, 문서·화면·풍경 등 비의류 사진은 거절해야 함.
- 서버는 제한 길이로 스트리밍 수신하고 실제 이미지 형식·디코딩 크기·픽셀 한도를 확인한 뒤 추론해야 함.
- 이미지 본문·base64·모델 원문 응답은 로그, D1, R2, KV, Analytics에 기록하지 않아야 함.
- 호출 한도는 인증 사용자 기준으로 적용하고, 속도 제한은 비용 회계와 구분해야 함.
- 승인된 로컬 사진 삭제·로그아웃·탈퇴 시 기기 사본도 정리해야 함.

## Constraints And Non-Goals

현재 사진은 서버 동기화 대상이 아니며 그 구조를 유지함. 얼굴 식별, 사람 속성 추론, 콘텐츠 수동 심사는 범위 밖임. 의미 판별은 확률적이므로 공격적 우회를 수학적으로 완전 차단한다고 주장하지 않음. 정확도와 지연은 실제 코퍼스로 측정해야 함.

## Before Architecture

[현재 구조 다이어그램](../diagrams/centralize-photo-acceptance-before.mmd)에서 모델 실패 경로와 저장 경로가 다시 합쳐짐. 이 합류점 때문에 서버 정책이 실패해도 저장이라는 권한 있는 상태 전이가 계속됨.

## Options

### Option 1: UI·프롬프트 보강

현재 API 형태를 유지하면서 프롬프트에 비의류 거절 문구를 추가하고, 낮은 신뢰도·`retake`·분석 오류에서 저장 버튼을 비활성화함. [옵션 1 구조](../diagrams/centralize-photo-acceptance-ui-guards-after.mmd)는 빠르고 되돌리기 쉬움. 정상 사용자의 실수는 줄지만 변조 앱은 결과를 만들거나 API를 직접 호출할 수 있고, 서버 자체에 승인 상태가 없으므로 보안 경계로 보기는 어려움.

| Change | Before | After | Security consequence | Cost |
| --- | --- | --- | --- | --- |
| 저장 UI | 분석 실패 후 직접 저장 | 실패 시 신규 사진 저장 차단 | 정상 UI 우회 감소 | 낮음 |
| 모델 프롬프트 | 의류 속성 강제 | 비의류 거절 지시 추가 | 일반 오분류 감소 가능 | 낮음 |
| 서버 권한 | 승인 개념 없음 | 그대로 없음 | 변조 클라이언트 위험 잔존 | 없음 |

### Option 2: 중앙 실패-폐쇄 승인 게이트

서버가 `decision`, `reasonCode`, `policyVersion`, 의류 속성을 함께 반환하고 앱은 `accept`가 아니면 신규 사진을 저장하지 않음. [옵션 2 구조](../diagrams/centralize-photo-acceptance-central-policy-gate-after.mmd)에서는 제한된 스트리밍 본문 읽기, base64 정규성·실제 이미지 시그니처·디코딩 크기·픽셀 한도, 사용자별 빠른 rate limiter와 D1 일일 예산, App Attest 신호, 의미 판별을 하나의 경계에서 소유함.

이 안의 매력은 정책 드리프트를 한곳에서 줄이는 점임. 모바일은 서버 결정을 보여주고 재촬영을 유도하지만 허용권을 만들지 못함. 로그는 사용자 ID 또는 비가역 집계 키, 정책 버전, 결과 코드, 바이트 구간, 지연시간만 남기고 본문과 모델 자유문은 남기지 않음. Cloudflare의 빠른 rate limiter는 로컬·eventually consistent라 남용 완화용으로만 쓰고, 비용 상한은 D1 일일 카운터로 별도 집행하는 편이 맞음.

남는 위험은 민감 사진이 의미 판별 전에 Workers AI에 도달한다는 점과 모델 오판임. 이를 완화하려면 화면에서 사람 없는 단일 물체 촬영을 강하게 안내하고, 보수적 신뢰도·다중 물체·사람 탐지 결과를 모두 실패-폐쇄로 묶어야 함. 롤백 시 API를 이전 응답으로 되돌리더라도 신규 사진 저장 차단은 유지해야 함.

| Change | Before | After | Security consequence | Cost |
| --- | --- | --- | --- | --- |
| 승인 소유권 | UI와 모델 응답에 분산 | 서버 정책 게이트가 소유 | 변조 클라이언트도 비승인 사진 저장 불가 | 중간 |
| 입력 검증 | 문자·길이, 전체 버퍼 | 제한 스트림·실제 이미지 검증 | 임의 바이너리·과대 본문 위험 축소 | 중간 |
| 남용 방지 | 없음 | 사용자 속도 제한+일일 예산 | AI 비용·DoS 범위 축소 | 중간 |
| 관측성 | 일반 오류 | 본문 없는 결과 코드·지연 | 사고 조사 가능, 사진 노출 최소화 | 낮음 |
| 개인정보 고지 | 요약·실제 흐름 불일치 | 업로드 직전+정책 문서 동기화 | 사용자 기대와 처리 흐름 정렬 | 중간 |

### Option 3: 온디바이스+중앙 이중 게이트

옵션 2 앞에 경량 온디바이스 의류·사람 탐지 모델을 둠. [옵션 3 구조](../diagrams/centralize-photo-acceptance-on-device-gate-after.mmd)에서 기기 게이트가 거절하면 JPEG/base64 생성과 네트워크 전송 자체를 중단하며, 통과한 사진도 서버가 다시 검증함.

개인정보 측면에서 가장 강한 안임. 특히 사용자가 실수로 사람·문서 사진을 선택했을 때 원격 처리 전에 차단 가능함. 그러나 iOS·Android 모델 패키징, 앱 용량, 저사양 기기 메모리, 모델 업데이트, 접근성 있는 오류 설명, 플랫폼별 정확도 회귀 비용이 생김. 온디바이스 판별도 확률적이므로 서버 재검증을 제거하면 안 됨. 모델 문제가 발생하면 기능 플래그로 기기 게이트만 비활성화하고 옵션 2 경계를 유지하는 롤백이 가능해야 함.

| Change | Before | After | Security consequence | Cost |
| --- | --- | --- | --- | --- |
| 첫 의미 판별 | 원격 AI | 기기+원격 AI | 실수로 선택한 민감 사진의 전송 감소 | 높음 |
| 앱 자원 | 이미지 조작만 | 로컬 모델·런타임 추가 | 앱 용량·메모리·배터리 증가 | 높음 |
| 실패 격리 | 서버 오류 시 수동 저장 | 기기 오류 시 옵션 2로 제한 롤백 | 저장 우회 없이 가용성 유지 가능 | 중간 |

## Comparison

| Dimension | Option 1 | Option 2 | Option 3 |
| --- | --- | --- | --- |
| Security | 정상 UI 실수만 일부 완화, 우회 잔존 | 승인·입력·남용 경계를 중앙화 | 옵션 2+원격 전송 전 1차 차단 |
| Performance | 거의 동일, 측정 필요 | 검증·카운터 지연 소폭 증가 예상, 측정 필요 | 온디바이스 추론 지연 추가, 기기군별 측정 필요 |
| Memory | 거의 동일 | 제한 버퍼와 검증 상태만 추가 | 모델 상주/로딩 메모리 증가 |
| Reliability | 모델 실패 시 기능 차단 | 실패-폐쇄라 오탐 시 재촬영 증가 | 기기별 모델 실패·정확도 편차 추가 |
| Operability | 낮음 | 정책 버전·rate limit·예산·거절률 운영 필요 | 옵션 2 운영+모바일 모델 배포·회귀 운영 필요 |
| Migration | 가장 쉬움 | API·상태 스키마·기존 사진 마이그레이션 필요 | 네이티브 빌드와 양 플랫폼 QA까지 필요 |

옵션 2의 비용은 중앙 게이트 구현과 보수적 거절로 인한 UX 마찰임. 다만 이 비용은 신규 사진 한 번당 발생하고, 저장 이후 추천 경로에는 영향을 주지 않음. 옵션 3은 개인정보 이득이 분명하지만 실제 기기 성능·정확도 자료가 없으면 한 번에 채택하기 부담스러움.

## Recommendation

현재 제약에서는 옵션 2를 권고함. 서버에 승인권을 두지 않으면 어떤 UI 보강도 변조 클라이언트와 미래 호출자에게 반복 적용되지 않음. 사람 사진의 원격 전송 자체를 금지해야 한다는 제품·법무 요구가 확정되거나, 실제 오선택 비율이 높게 측정되면 옵션 3이 더 적합함.

| `E4` — 무결성 monitor | unaffected | mitigates | mitigates | 실패율·지원기기 근거 전까지 별도 단계적 enforce |

옵션 2·3에서도 adversarial image, 모델 미탐, 계정 탈취, 기기 자체 탈옥·루팅, OS 백업 정책 위험은 남음. App Attest 강제는 기존 모니터 데이터와 미지원 기기 실패 동작을 검증한 뒤 별도 결정해야 함.

## Migration And Rollout

기존 사진은 `legacy-unverified`로 표시하되 즉시 삭제하지 않고 편집·재분석 시 새 정책을 적용하는 편이 안전함. 서버는 먼저 새 응답을 구버전 앱과 호환되게 배포하고, 모바일이 새 `policyVersion`을 이해한 뒤 신규 사진 저장을 실패-폐쇄로 전환해야 함. 거절률·오류율·p95 지연·사용자 이탈을 카나리로 확인한 뒤 전체 적용함. 롤백은 서버 정책 버전과 모바일 기능 플래그로 수행하되 수동 저장 우회는 되살리지 않음.

## Validation Plan

- 허용 코퍼스: 상의·하의·아우터·신발·가방·액세서리, 배경·조명·각도·재질 다양화.
- 거절 코퍼스: 사람·얼굴·신체, 문서·신분증, 풍경, 음식, 동물, 화면 캡처, 다중 물체, 흐림·과도한 크롭, 민감 콘텐츠.
- 변조 입력: 잘못된 base64, MIME 불일치, JPEG polyglot 후보, 과대 픽셀, chunked 과대 본문, 반복·병렬 호출.
- 상태 회귀: reject/review/timeout/502/429에서 신규 사진·메타데이터가 SQLite와 문서 디렉터리에 남지 않아야 함.
- 개인정보 회귀: Worker 로그·D1·Analytics·오류 응답에 base64, 이미지, 모델 자유문, 파일 경로가 없어야 함.
- 성능 기준은 출시 전에 보급형 Android와 지원 최저 iPhone에서 p50/p95 준비·업로드·분석 지연, 피크 메모리, 앱 크기를 측정해 확정함.
